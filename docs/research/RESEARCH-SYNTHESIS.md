# Optical file transfer research synthesis

Research snapshot: 2026-07-31. This note records the evidence used to choose the first implementation. Sources are primary papers, standards, official platform documentation, and first-party implementations where available.

## What the literature says

- LCD/camera links are not ordinary barcode scans. Perspective changes the sampling pitch across the frame, blur mixes neighbouring cells, ambient light adds a large DC component, and rolling shutter can sample different display states by row. PixNet explicitly models perspective and blur and reports up to 12 Mb/s with a large LCD and commodity cameras at 10 m, but its evaluation uses a specialized OFDM-style link and is not a direct promise for handheld browser cameras. [PixNet paper](https://people.csail.mit.edu/nabeel/pixnet-mobicom10.pdf), [capacity under perspective](https://www.sciencedirect.com/science/article/abs/pii/S1574119214001849)
- COBRA adapted block size and barcode layout for low-speed smartphone cameras, rather than assuming a static QR image. RainBar combined frame tracking bars, in-frame locators, progressive localization, HSV colour extraction, CRC, and Reed–Solomon; its paper is a strong argument that marker/layout/synchronization are part of the code, not a separate prelude. [COBRA DOI](https://doi.org/10.1145/2307636.2307645), [RainBar DOI](https://doi.org/10.1109/ICDCS.2015.61)
- HiLight and DeepLight show a different point in the design space: alpha/blue-channel imperceptible modulation can ride on normal content, but the imperceptible channel trades away payload and demands calibration or learned decoding. DeepLight reports at least 0.95 Kbit/s in its evaluated setting, far below a visible dense transfer stream, so it is not the V1 payload mode. [HiLight paper](https://www.cs.dartmouth.edu/~xia/publication/mobisys15-hilight/mobisys15-hilight.pdf), [DeepLight](https://arxiv.org/abs/2105.05092)
- Cimbar is the closest practical reference for an offline file sender: its first-party implementation documents coloured tile matrices, Reed–Solomon, CRC/hash checks, Wirehair fountain coding, compression, WASM encoding, an Android decoder, and approximately 850 kbit/s in its stated setup. Its architecture validates unordered fountain recovery, but the decoder is not shared with the web encoder and colour classification is not continuously calibrated. [libcimbar](https://github.com/sz3/libcimbar), [Cimbar decoder](https://github.com/sz3/cfc)
- Strata makes a useful systems point: hardware diversity requires independently decodable layers, because camera resolution and frame rate vary. We use the simpler V1 equivalent—capability-advertised grid/levels/block size with a robust fallback—before attempting fully layered modulation. [Strata summary and citation](https://www.researchgate.net/publication/324044248_Lightweight_Display-to-device_Communication_Using_Electromagnetic_Radiation_and_FM_Radio)
- Display-camera measurement work identifies moiré, rolling shutter, blocked regions, autofocus, trembling, and vibration as unstable factors. A reproducible simulator must vary these rather than report a clean renderer-only bitrate. [systematic performance measurement](https://arxiv.org/abs/1501.02528)
- RaptorQ is standardized for object delivery and is attractive for large streams, but implementing the full RFC in two runtimes is a larger compatibility surface than V1 needs. The first implementation uses a deterministic sparse XOR fountain with a systematic prefix and a Gaussian-elimination decoder, leaving RaptorQ as a measured replacement candidate. [RFC 6330](https://datatracker.ietf.org/doc/rfc6330/)
- The browser can request camera tracks, enumerate devices after permission, inspect settings/capabilities, and apply constraints, but it cannot guarantee a requested resolution or frame rate and camera access requires a secure context. Android CameraX exposes a CPU-accessible `ImageAnalysis` stream and explicitly supports dropping stale frames with `STRATEGY_KEEP_ONLY_LATEST`; Camera2 exposes AE lock and related controls. [getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), [constraints](https://developer.mozilla.org/en-US/docs/Web/API/Media_Capture_and_Streams_API/Constraints), [CameraX image analysis](https://developer.android.com/media/camera/camerax/analyze), [Camera2 CaptureRequest](https://developer.android.com/reference/android/hardware/camera2/CaptureRequest)

## Resolved Version 1 protocol

1. **Visible hybrid tile stream.** The baseline carries one packet per visible frame. Data cells use four calibrated luminance levels (2 bits/cell) for robust mode. Dense mode uses sixteen levels (4 bits/cell) only after the decoder reports sufficient margin. Colour is reserved for four high-saturation corner fiducials and is not relied on for payload classification.
2. **Layout.** A quiet dark surround contains four unique coloured corner markers, a grayscale calibration strip, a compact header lane, and a rectangular data lattice. The markers provide screen bounds and orientation; the calibration strip estimates local black/white and intermediate levels on every frame. The data lattice is sampled through a projective homography, so rectangular and trapezoidal views share the decoder.
3. **Synchronization.** Frames carry a session id and monotonically increasing sequence number. A receiver accepts any valid frame in any order, ignores duplicates, and does not assume display refresh equals camera FPS. V1 repeats the same packet on a deterministic schedule and rejects low-confidence frames; rolling-shutter phase estimation and preamble-free decoding are experimental modes.
4. **Inner protection.** Packet bytes are encoded with Hamming(8,4) on each nibble, then guarded by CRC-32. The decoder returns correction counts and confidence margins. This is deliberately lightweight, portable, and testable; a Reed–Solomon or LDPC inner code can replace it behind the same packet interface after benchmarks.
5. **Cross-frame recovery.** File bytes are split into fixed source blocks. Systematic packets are sent first, followed by deterministic sparse-XOR repair packets whose coefficient sets are derived from session id, sequence, and source count. The receiver stores equations and performs incremental GF(2) elimination. This provides order independence, duplicate tolerance, and no reverse channel. RaptorQ is a roadmap experiment, not a V1 dependency.
6. **Integrity.** A received file is accepted only after exact length and SHA-256 verification. CRC is an error detector for individual optical packets; SHA-256 is an end-to-end file identity check, not custom cryptography.
7. **Adaptation.** The sender advertises grid dimensions, levels, block size, and nominal cadence in the header. The receiver records observed camera size/FPS, duplicate/drop/rejection counts, homography confidence, calibration margins, correction counts, and verified goodput. It can request a local fallback mode only through user selection in V1; no radio feedback channel is assumed.

## What is genuinely new here

- The first implementation treats the marker geometry, per-frame radiometric calibration, confidence, and file-level fountain equations as one diagnosable pipeline instead of a barcode decoder plus a separate transfer loop.
- Payload uses grayscale for stable classification while reserving saturated colours exclusively for geometry. This avoids making white balance a payload dependency but still gives low-cost automatic detection.
- The simulator emits a confusion matrix and confidence distribution for each candidate symbol mode. Candidate changes are retained only when verified goodput or reliability improves under the same seeded impairment suite.
- The protocol has a robust fallback (2-bit cells) and a dense candidate (4-bit cells) behind one frame grammar, making the 16-level idea measurable instead of assumed.

## Explicitly rejected for Version 1

- Animated QR: useful as a baseline fixture, but its finder/format overhead and single-code capacity do not exploit an independently sampled high-density lattice.
- Imperceptible alpha/blue modulation: valuable for overlays, but not appropriate for maximum file goodput.
- Full DNN/StegaStamp decoding: too costly and difficult to make deterministic/offline across browser and Android for the first working build.
- Full RaptorQ: standard and promising, but a second independent implementation before measuring V1's sparse-XOR failure modes would add complexity without evidence of a bottleneck.
- Dedicated OFDM/rolling-shutter exploitation: promising on controlled hardware, but fragile on ordinary browser webcams and requires more camera timing control than web APIs guarantee.
