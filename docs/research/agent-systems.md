# Screen-to-camera systems: protocol, throughput, and phone relevance

Research snapshot: 2026-07-31. This note is for the CamSend Wayfinder map. It prioritizes primary papers, author-hosted manuscripts, official project pages, and first-party source repositories. “Throughput” is not one uniform metric across the literature: some papers report correctly decoded bits per second, some report raw channel rate, and some report end-to-end file goodput. Those numbers are labeled below and should not be compared as if they were one benchmark.

## Bottom line for CamSend

The most transferable design is a visible, screen-filling, tiled frame stream with strong geometry, an explicit frame identifier, per-frame integrity checks, confidence/erasure handling, and unordered outer recovery. Cimbar is the closest first-party file-transfer implementation; RainBar and MAMBA show how much can be won by treating localization, synchronization, block sizing, and feedback/adaptation as part of the protocol; RescQR shows that composite frames can be recovered instead of always discarded.

The headline rates from PixNet, hidden-channel systems, and controlled visual-MIMO experiments are valuable research bounds, not promises for an ordinary browser webcam. Modern phones improve pixel count and CPU, but the recurring bottleneck remains the camera/display channel: cell footprint, perspective, motion/defocus blur, rolling-shutter mixtures, exposure/white balance, display response time, frame drops, and the cost of decoding every captured frame.

CamSend’s accepted V1 direction in [ADR-0001](../adr/0001-version-one-optical-protocol.md)—visible calibrated luminance tiles, projective geometry, packet CRC, Hamming protection, and sparse-XOR fountain recovery—is a sensible portability point. It deliberately keeps the proven system ideas while avoiding assumptions that require a second radio, a trained decoder, a special display, or a global camera/display clock.

[Performance notes](https://github.com/sz3/libcimbar/blob/master/PERFORMANCE.md) | The camera, not a newer CPU, is usually the bottleneck. Eight-color mode was removed from the preferred path because it was inconsistent. COBRA adapts block size/layout for blur and uses lightweight preprocessing and real-time Android decoding. [Paper record and abstract](https://doi.org/10.1145/2307636.2307645), [RainBar’s primary comparison](https://www.researchgate.net/publication/283877651_Rain_Bar_Robust_Application-Driven_Visual_Communication_Using_Color_Barcodes) | The accessible COBRA paper record states Android evaluation but does not expose a single headline rate. Motion blur, frame switching, and the lack of a shared display/capture clock hurt localization and usable frame rate. | **RainBar** | Application-driven color barcodes with in-frame code locators and tracking bars. The receiver uses progressive locator detection, HSV-based color extraction, a 3×3 mean filter, CRC plus Reed–Solomon, and a blur assessment. The paper separates fast stream reception from reliable file transfer: failed frames are intended to be retransmitted using a proposed smartphone LED/light-sensor feedback link. [Primary paper](https://www.researchgate.net/publication/283877651_Rain_Bar_Robust_Application-Driven_Visual_Communication_Using_Color_Barcodes) | At 6×6-pixel blocks the paper reports **955.68 kbit/s**; at 12×12 it reports **262 kbit/s**; at 15×15 it reports **164.67 kbit/s**. Decoding remains above **91% at 18 display frames/s** in its tested setup. The reported throughput is successfully decoded data per second in received frames, not a SHA-256-verified file goodput. [Primary paper](https://www.researchgate.net/publication/283877651_Rain_Bar_Robust_Application-Driven_Visual_Communication_Using_Color_Barcodes) | The paper’s real-time decoder takes about 80 ms per frame in its stated implementation, limiting that path to about 12 fps. Higher display rate increases nominal throughput but lowers decoding rate; larger blocks improve correctness but reduce capacity. The proposed LED/light-sensor feedback path is extra hardware/OS behavior and was discussed as ongoing implementation work. | **Very relevant ingredients:** put locators, timing, confidence, error detection, and block-size adaptation inside the frame grammar. Do not inherit its extra feedback assumption; CamSend needs to finish without a reverse channel. |
| **PixNet** | Spatial OFDM-like modulation: 4-QAM symbols are arranged in a Hermitian 2D frequency matrix and transformed by a 2D IFFT into real display luminance. The receiver detects corners, corrects perspective by generalized sampling-frequency correction, uses a cyclic prefix against inter-symbol interference, and uses blur-adaptive redundancy; ambient-light DC is discarded. [Author-hosted paper](https://groups.csail.mit.edu/netmit/wordpress/wp-content/themes/netmit/papers/full_paper5_pixnet.pdf) | Prototype result: **up to 12 Mbit/s at 10 m** and **8 Mbit/s at a 120° view angle**, using a Dell 30-inch LCD and consumer cameras. The paper reports 2–9× the throughput of a QR baseline in its experiments. [Paper](https://groups.csail.mit.edu/netmit/wordpress/wp-content/themes/netmit/papers/full_paper5_pixnet.pdf) | It assumes the camera is already set up to view the screen, uses one-way communication, and assumes acknowledgements/uplink can use RF WLAN. The evaluation uses large LCD pixels, camera hardware, and a substantial frequency-domain receiver. Perspective, blur, focus, and geometric extraction still dominate the link. [Problem-domain assumptions](https://groups.csail.mit.edu/netmit/wordpress/wp-content/themes/netmit/papers/full_paper5_pixnet.pdf) | **A useful upper-bound/reference, not a V1 implementation.** Modern phones can run FFTs, but browser capture does not guarantee fixed timing, raw resolution, or exposure control, and a portable file link cannot assume WLAN acknowledgements. Its strongest transferable ideas are projective correction, frequency-selective robustness, and ignoring unstable DC/low-confidence observations. |
| **HiLight** | Hidden communication layer atop arbitrary content. A black, transparent-by-default alpha layer is divided into grids; alpha changes are rendered by the GPU and modulated with BFSK at the screen refresh rate, with scene-change deferral and receiver-side adaptive filtering/MVDR. [Primary paper](https://www.cs.dartmouth.edu/~xia/publication/mobisys15-hilight/mobisys15-hilight.pdf) | With 120 grids, the paper reports about **1.1 kbit/s and 91%+ accuracy** for brighter static content, about **1 kbit/s and 84% accuracy** across dynamic scenes, and up to **4–4.5 kbit/s** with 600 grids while accuracy falls to about 67–75%. It supports about 1 m, 60° viewing angle, and stable behavior above 40 lux in the tested indoor setup. [Evaluation](https://www.cs.dartmouth.edu/~xia/publication/mobisys15-hilight/mobisys15-hilight.pdf) | The signal is intentionally near the perceptual threshold. Dark content, camera noise, screen refresh rate, ambient light, scene changes, adjacent-grid interference, and distance reduce margin. The original receiver uses an iPhone 5s and the transmitter/receiver pipeline is tied to mobile graphics/camera behavior. | **Phone-relevant but objective-mismatched.** Alpha-layer rendering is practical for unobtrusive metadata, not maximum visible file goodput. It supports CamSend’s separation of content and transport as a future mode, but V1 should not sacrifice symbol margin for invisibility. |
| **Strata** | Layered/hierarchical visual coding. Multiple spatial granularities and/or temporal layers are embedded in one code; layers are independently decodable and recursively extendable. Large blocks/low-frequency structure serve distant or low-resolution receivers, while finer layers add capacity for better links. [Primary abstract and record](https://www.researchgate.net/publication/266661408_Strata_Layered_coding_for_scalable_visual_communication) | The accessible primary record does not give a headline bitrate. It claims a wider operating range and a corresponding rate for the available capture resolution/frame rate, explicitly at the cost of lower capacity than a single-layer code. That missing absolute rate is preferable to inventing one from later surveys. [Primary record](https://doi.org/10.1145/2639108.2639132) | The code must manage interference between layers and spends capacity on scalability. Device resolution, frame rate, distance, and layer separation are coupled. | **Conceptually relevant to capability adaptation.** CamSend’s robust/dense modes are a simpler, explicit two-level version of the same idea. A fully recursive Strata-style codec is a later optimization after measurements show that a single grid cannot cover the target phone strata. |

## Newer and more practical systems

### TXQR: the simple open baseline

[TXQR](https://github.com/divan/txqr) is a first-party Go protocol and tool/library set for transferring data as animated QR codes. It uses fountain codes rather than requiring every frame in order, and the repository includes a mobile subdirectory plus a Gomobile-based iOS reader demo. The source does not claim a universal throughput number; its value is a small, inspectable baseline with an explicit answer to frame loss and receiver start time. It is highly relevant for a QR fallback and for testing whether CamSend’s custom tile decoder earns its complexity. Its bottleneck is QR finder/format overhead and the number of modules available per frame, not the fountain layer.

### ShiftCode: exploit rolling-shutter mixtures instead of discarding them

[ShiftCode](https://doi.org/10.1145/3191784) uses shifting shape patterns in a dynamic barcode. Its pattern-based layout and decoder are designed for the frame-mixture problem caused by a CMOS rolling shutter; two-level reliability combines intra-frame correction with inter-frame redundancy. The authors implemented it on Android and report at least a **two-fold goodput improvement** over conventional screen-camera systems, but the accessible primary abstract does not expose one absolute rate. The technique is attractive when a phone camera captures several display states in one frame; the cost is a more specialized symbol grammar and decoder. CamSend should first reject mixed frames deterministically, then benchmark ShiftCode/RescQR-like recovery as an optional mode.

### MAMBA: adaptation and bidirectional control

[MAMBA](https://aaltodoc.aalto.fi/items/70f03bfb-2b31-4f53-92f6-b3a1119dd1e7) is a mobile framework for adaptive camera-display communication with a custom five-color barcode, corner tracking, and a decoder whose work scales with the number of blocks rather than the total captured pixel count. It uses a connection-oriented, bidirectional protocol with fast feedback and adapts frame rate and frame length to environmental conditions and device processing capability. The paper claims reliable real-time operation across varied conditions but does not state a single headline rate in the accessible abstract. This is directly relevant to modern phones: higher camera resolutions can be used without making every pixel equally expensive. Its non-transferable assumption for CamSend V1 is the reverse optical control path; CamSend should retain local diagnostics and user-selected fallback instead.

### RescQR: recover composite frames

[RescQR](https://hhannuaa.gitlab.io/papers/tmc2024_hhan.pdf) keeps standard QR modules but adds a dedicated border: alternating border squares carry color references and a frame ID. A repeated QR carousel lets the receiver start at any time; mixed frames are separated using the border, blurred transition regions are inferred with a Viterbi procedure, and partial frames are assembled as a jigsaw-like data cube. A front camera estimates distance for auto-configuration. The authors report **400+ kbit/s data goodput** with standard QR codes. [Primary paper record](https://www.researchgate.net/publication/370852344_RescQR_Enabling_Reliable_Data_Recovery_in_Screen-Camera_Communication_System)

RescQR is unusually relevant to current phones because it addresses the actual rolling-shutter/display-refresh failure mode rather than assuming a clean still image. Its costs are a more complex decoder, dependence on a border and frame references, and display response-time effects: the paper notes larger blurred bands on LCD than OLED. It is a strong challenger for a later CamSend mode, especially if camera traces show that discarded mixed frames dominate lost goodput.

### ChromaCode: high-rate hidden embedding

[ChromaCode](https://walleve.github.io/ChromaCode/) embeds a binary imagery code into ordinary video using CIELAB/CIEDE2000 perceptual distance, adapting embedding to pixel lightness and regional texture. A concatenated convolutional plus Reed–Solomon code handles channel errors. At its default 50 cm setup, the primary paper reports **777 kbit/s raw throughput, 120 kbit/s goodput, and BER 0.05**; changing the perceptual threshold moves raw throughput roughly 734–846 kbit/s and goodput 94–151 kbit/s. [Author-hosted paper](https://cswu.me/papers/mobicom18_chromacode_paper.pdf)

This is evidence that modern phone cameras can recover a substantial unobtrusive side channel, but it is a different optimization target from visible file transfer. Goodput is reduced by concatenated-code parity and content-dependent embedding, and the full pipeline must model video texture, color space, screen/camera distortion, and flicker perception. Keep it as a future “hide the transfer” mode, not as the default Wayfinder link.

### AIRCODE: visual data plus inaudible audio control

[AIRCODE](https://www.usenix.org/conference/nsdi21/presentation/qian) combines an invisible visual data channel with an inaudible audio control channel. Audio provides reliable low-rate coordination while the visual channel carries high-rate data; visual odometry tracks the screen under dynamic content and surrounding interference. Experiments on commercial monitors and smartphones report **1,069 kbit/s at BER 5%**. The protocol is impressive, but its key assumption is exactly what CamSend excludes: a speaker/microphone path and a receiver that can use it. The useful lesson is architectural—put synchronization/configuration on a robust low-rate side channel when one exists—but V1 must solve the same problem with visible markers, frame IDs, repeated metadata, and unordered recovery.

### DeepLight: learned whole-frame hidden decoding

[DeepLight](https://arxiv.org/abs/2105.05092) modulates only the blue channel, detects the screen with an object-detection model, and uses a DNN to decode all spatial bits jointly instead of isolating each bit cell. The paper reports screen IoU of at least 83%, frame error rate below 0.2, and **at least 0.95 kbit/s goodput** with a human-held smartphone camera at about 2 m. The model reduces sensitivity to imperfect screen extraction, but requires trained models, a compatible inference runtime, and a training distribution that covers displays, cameras, content, and motion. Modern phones can execute compact networks, but a deterministic browser/Android reference decoder is easier to validate and diagnose for CamSend V1.

### WinkLink: low-SNR optical communication behind arbitrary backgrounds

[WinkLink](https://ruixiao24.github.io/files/winklink-mobisys24.pdf) is LED-camera OCC rather than screen file transfer. It modulates RS-FSK, trains a DNN signal extractor on synthetic scenes, and uses context-aware demodulation to recover weak repeated stripe signals behind unseen dynamic backgrounds. With a 10 W light it reports a range exceeding 11 m; with 60 fps video, tested symbol durations yield **60, 120, and 240 bit/s**, with the fastest mode requiring higher SNR because of phone-camera frame gaps. The contribution is practical background robustness, not high payload density. It matters to CamSend as a warning that a clean black/white code region is a design choice: if CamSend ever overlays arbitrary content, background separation becomes a learned low-SNR problem.

### PassiveCam: ambient-light transparent displays

[PassiveCam](https://arxiv.org/abs/2403.16185) demonstrates screen-to-camera communication using transparent displays that rely on ambient light rather than a powered backlight. Its Android application improves existing unobtrusive encoding and reports about **90% packet success**, with response times of 530 ms for a static camera and 1,071 ms for a handheld camera. It proves that the receiver side can run in real time on a smartphone, but the passive display has lower and less-controlled image quality because illumination is environmental. This is a future deployment variant, not a reason to weaken CamSend’s active-display assumptions.

### EventOCC: high-rate but non-phone event cameras

The [EventOCC first-party project page](https://mpl.sist.shanghaitech.edu.cn/Software.html) links the authors’ [implementation](https://github.com/suhang99/EventOCC). It uses an event camera for dynamic visual marker tracking, localization, and communication rather than a conventional frame camera. The authors report up to **114 kbit/s in static conditions**, 1 cm localization accuracy, and 1% bit error rate under camera motion. This is a compelling research direction for high-speed receivers, but event-camera hardware is not a modern-phone baseline. It should not influence V1’s browser or Android capture contract.

## Cross-system conclusions

### Protocol features that survive on modern phones

- **Explicit geometry:** corner markers, borders, timing references, or a projective quadrilateral are not overhead to be optimized away; they are what makes sampling possible under perspective and crop. PixNet, COBRA, RainBar, Cimbar, and RescQR all make localization part of the link.
- **A real frame protocol:** include session/version, frame sequence, mode, geometry, payload length, and a fast integrity check in every frame or repeated header. Receivers start late, drop frames, duplicate frames, and observe mixtures.
- **Adapt cell size and cadence:** larger cells improve blur and perspective margin; slower display cadence improves capture integrity; high-resolution cameras can pay for denser grids. RainBar and MAMBA show the value of adaptation, while Strata shows the more elaborate layered version.
- **Use soft decisions and erasures:** a borderline color/luminance/tile observation should contribute confidence or become an erasure. Hard decisions turn a recoverable weak frame into a false packet that can poison file assembly.
- **Separate inner and outer recovery:** CRC/RS/Hamming-like protection handles a frame; fountain or rateless recovery handles missing/out-of-order frames and avoids depending on an uplink. Cimbar and TXQR demonstrate the practical value of this split.
- **Measure verified file goodput:** raw bits per displayed frame, decoded bits per captured frame, and end-to-end bytes per second are different. CamSend should time from first displayed transfer frame to exact-length, SHA-256-verified reconstruction and report rejection, duplication, frame-mixture, CPU, and recovery statistics.

### Features that do not transfer cleanly to CamSend V1

- **PixNet’s headline rate** depends on a large LCD, a frequency-domain receiver, and a one-way link whose acknowledgements may use WLAN.
- **HiLight, ChromaCode, DeepLight, and AIRCODE** optimize hidden or unobtrusive communication. Their lower visual margin, perceptual constraints, model dependencies, or audio control path are not appropriate as the visible maximum-goodput default.
- **RainBar/RainBar+ style feedback** is useful when a second optical/acoustic path is available, but a screen-only browser link cannot require it.
- **Event-camera and specialized LED systems** move the receiver or transmitter outside the ordinary screen plus phone-camera contract.
- **Very high-order color alphabets** are not free. Cimbar’s own first-party notes prefer four colors and call eight-color mode inconsistent; exposure, white balance, color gamut, glare, and mixed frames collapse color margins before modern CPU becomes the limiting factor.

## V1 gap and measurable next steps

The gap is not another nominal symbol alphabet. It is a portable, diagnosable screen-wide file protocol that combines the best ordinary-phone techniques under no-radio, no-network, no-clock, no-feedback assumptions:

1. Keep the visible calibrated tile stream and projective corner geometry.
2. Benchmark robust 2-bit luminance against dense 4-bit luminance and a Cimbar-like glyph/color challenger using the same screen area and the same capture traces.
3. Carry a frame sequence and end-to-end file identity in every transfer; accept frames in any order and ignore duplicates.
4. Record confidence, erasures, blur/mixed-frame status, and calibration margin instead of only decoded bytes.
5. Add RescQR/ShiftCode-style mixed-frame recovery only if traces show that discarded composite frames are the dominant loss.
6. Add Strata/MAMBA-style capability adaptation only after a fixed robust mode is measured across real camera resolutions, frame rates, distances, angles, exposure states, and phone CPU budgets.

The success criterion should be verified goodput and file-success probability over an impairment matrix, not the best clean-lab rate. A mode that reports 1 Mbit/s but fails to reconstruct a file under common handheld conditions is less useful than a slower mode that completes reliably and explains why a frame was rejected.
